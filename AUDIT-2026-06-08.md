### Topology summary
- **Edge:** Vercel `outputDirectory: public` — all HTML, JS, CSS, and 1.3 MB of pre-baked JSON served as static
- **Functions:** 2 Python functions (`api/search.py` 769 lines, `api/health.py` 34 lines) — stdlib only, no `requirements.txt`
- **Rewrites:** 12 clean HTML URLs + 6 fake-API rewrites (`/api/live/*`, `/api/market/*`, `/api/deal/*`, `/api/stats`, `/api/categories`, `/api/sources` → `public/data/*.json`)
- **Database:** Supabase Postgres + PostgREST. Read by browser via anon key + read by GH Actions via service-role key. **`/api/search` does not query the DB** — schema header's claim that "Vercel reads `v_latest_source_data`" is aspirational.
- **No backend server.** No Render. No Fly. The Render backend (`api/server`, `api/property`, `render.yaml`) was retired in Phase 4.

### Two reliability patterns worth naming
1. **Rates via cache, not live.** `api/search.py:155-176` reads `/api/live/ticker` (edge-cached, cron-refreshed) first for FRED rates because FRED is slow/sometimes blocked from Vercel IPs.
2. **Non-blocking shutdown + 13s budget.** `api/search.py:637-650` uses `cf_wait` + `ex.shutdown(wait=False, cancel_futures=True)` so the function returns even if FEMA-NFHL or EPA sockets hang — they report `error`, the response gets `degraded: true` if <3 sources succeed, but the user gets a response.

### Critical gaps

1. **`data_records` is created lazily at runtime** in `pipeline/flatten_records.py:32-37` — not in `schema.sql`. No FK to `sources.name`, no `fetched_at`, no indexes. Written by 4 scripts (`flatten_records.py`, `deep_records.py`, `socrata_discover.py`, `rest_load_records.py`); read by browser (`wall.html:66-72` paginates up to 20k rows). A fresh DB applied from `schema.sql` alone has no RLS on this table until the cron runs.
2. **Missing composite index `(source_id, fetched_at DESC)`** on `source_data` — yet `v_latest_source_data` uses exactly that pattern (`DISTINCT ON (sd.source_id) … ORDER BY sd.source_id, sd.fetched_at DESC`). At current scale (~20k rows) Postgres copes; at 100k+ it's a full-table sort on every dashboard load.
3. **Two parallel write paths to `sources`** with different merge semantics: `rest_load_catalog.py:56` (PostgREST replace-all) vs `load_sources.py:74-81` (`COALESCE(NULLIF(EXCLUDED.X,''), sources.X)` preserve-non-empty). Whichever runs last wins. PostgREST path can clobber non-empty fields to empty.
4. **Two scripts write `public/data/stats.json`**: `scripts/build_registry.py:82-90` (shape A) and `pipeline/import_catalog.py:99-103` (shape B with **hardcoded `last_updated: "2026-06-08T00:00:00Z"` literal**). Cron only runs the latter — last-writer-wins indefinitely with a frozen timestamp.
5. **Anon `SELECT * FROM source_data` is wide-open** including `payload JSONB`. Socrata-discovered municipal datasets historically leak PII (license records, code-enforcement complaints). Any visitor with the anon key can `curl /rest/v1/source_data?select=payload&limit=10000`.
6. **No migration framework.** `schema.sql` is the only SQL file. Header comment says "Apply once." Any change is a manual edit + manual re-apply.
7. **`v_coverage` is defined but no code reads it** (the dashboard uses static `/data/categories.json` from cron, not the view).
8. **No Storage / Edge Functions / Realtime usage** — pure Postgres + PostgREST.

### Volume reality check
- `sources`: ~1,932 rows (trivial)
- `ingest_runs`: ~365/year × 4 tier passes = ~1,460/year (trivial)
- `source_data`: at 1,932 sources × 365 daily × 4 passes = up to ~2.8M rows/year — **needs retention policy**
- `data_records`: ~275k rows per refresh (DELETE-then-INSERT per source) — **needs indexes today**

# 14. Performance Review

### Payload reality

| Layer | Size | Notes |
|---|---|---|
| HTML (15 files) | 241 KB | Largest: `explore.html` 47 KB, `site.html` 39 KB |
| JS (7 files) | 96 KB | Unminified; largest `viz.js` 28 KB |
| CSS | 14.6 KB | `rp-shell.css` only |

| Images | 324 KB | 5 JPEGs; one (`om_p9_img1.jpeg` 203 KB) over threshold |

### Critical perf findings

1. **CRITICAL — 661 KB JSON parsed eagerly on the main thread.** `public/data/sources_catalog.json` is fetched and parsed in full by `sources.js:111` on every visit to `/sources` and any page that mounts `#rp-sources`. Combined with `sources.json` (312 KB) and `sources_all.json` (134 KB) parsed on dashboard/explore/site/wall: **~1.1 MB JSON parse cost per page load**. The wire size is smaller (Vercel gzips it ~30-40%), but the parse cost is the uncompressed size.
2. **CRITICAL — Chart.js loaded synchronously in `<head>`.** `dashboard.html:9` loads Chart.js 4.4.1 (~200 KB gzip) from cdnjs, blocking first paint by 100-400ms. Then `viz.js:296` and `panels.js:17` each re-load Chart.js at runtime — three independent load paths racing.
3. **CRITICAL — Zero `async`/`defer` on any `<script>` tag** across all 15 HTML pages. Every page has 4-6 render-blocking scripts.
4. **CRITICAL — `data_records` has no indexes** but `wall.html:66-72` paginates up to 20k rows with `offset` (quadratic) and `viz.js:303, 365` does `count=exact` every 60s. Full-table scans on every tab.
5. **HIGH — `viz.js:364-371` 60s polling never pauses on hidden tabs.** Same for `globe.js` RAF (Three.js) and `rp-shell.js:141-170` (60-particle canvas).
6. **HIGH — Google Fonts blocking render** on all pages; no `&display=swap` → FOIT.
7. **HIGH — `om_p9_img1.jpeg` 203 KB baseline JPEG**, 1365×784, no WebP/AVIF, no `srcset`, no `loading="lazy"`.
8. **MEDIUM — No SRI on Chart.js / Three.js / D3** (only Leaflet has it). Supply-chain risk + cross-origin cache won't reuse.
9. **MEDIUM — Missing composite index `(source_id, fetched_at DESC)`** on `source_data` — exact pattern of `v_latest_source_data`.
10. **MEDIUM — `index.html:227-303` fires 6 unbatched `fetch()` calls on load** + a 6-URL `Promise.all` for health pings. 6 layout reflows in first 2s.
11. **LOW — No `Cache-Control` on `/data/*.json`** beyond Vercel default. Static JSON gets no `immutable` cache hint.
12. **LOW — Duplicate JPEGs.** `om_p5_img1.jpeg` and `om_p7_img1.jpeg` are byte-identical 10,151 B.

### Cold start

`api/search.py` is already optimal. Stdlib-only, no module-level network/DB calls. Cold start estimated 150-350ms; total user-visible TTFB on cold is dominated by the 13s fan-out budget, not init. User-visible p50 ≈ 8-10s cold, 100-300ms warm-cached.

### Top 5 perf wins

1. **Add `defer` to every script tag**; remove sync Chart.js from `dashboard.html:9` and load it once via `viz.js` with an `IntersectionObserver` gate. **Expected LCP improvement: 400-800ms on /dashboard.**
2. **Chunk `sources_catalog.json`** into `_index.json` (5 KB) + per-category files. Cuts `/sources` initial payload from 661 KB → 5 KB. **Expected FCP/TTI improvement: 500ms-1s on slow networks.**
3. **Add Vercel `headers` block** with `Cache-Control: public, max-age=31536000, immutable` on `/data/*.json` + `/rp-shell.css`; add `?v=<sha>` cache-busting. **Repeat-visit TTFB: -200 to -400ms.**
4. **Gate 60s polling loops behind `document.visibilityState === 'visible'`** in `viz.js`, `globe.js`, `rp-shell.js`. Add composite index `(source_id, fetched_at DESC)` on `source_data` + `(source_name)`, `(category)` on `data_records`. Cuts background DB load 10×.
5. **Replace `om_p9_img1.jpeg` (203 KB)** with WebP (~50 KB) + AVIF (~30 KB) via `<picture>`; add `loading="lazy"` + `decoding="async"` to all non-hero images. **Expected /terminal LCP: -300-600ms.**

# 16. Product Review

### What the project actually is, today
A public, unauthenticated CRE data terminal. It's three things stacked:
1. **A genuinely good live-search API** (`/api/search`) that fans out to ~22 government + market data sources in 13s with honest degradation
2. **A real ingestion pipeline** that builds a Supabase warehouse from 1,932 cataloged sources via a daily GitHub Actions cron
3. **A heavy marketing chrome** around both, with some pages (Explore, Data Coverage, Wall) doing real product work and other pages (Site, Terminal, Index) presenting hardcoded sample data as if it were live

### The pitch that's defensible
> "RePrime is a free, public CRE data terminal. Type any U.S. address and we fan out in ~13 seconds against 22 government and market APIs — FEMA flood, USGS, NWS, OSM, GDELT news sentiment, Census ACS, FRED rates, FDIC banking, and more — to give you flood risk, demographics, financing context, news, and POIs in a single response. Behind it, we maintain a catalog of 1,932 free data sources, with a daily ingestion pipeline writing curated datasets (Treasury yield curve, REIT financials from SEC EDGAR, FRED macro indicators) to a Supabase warehouse. Everything is open-source under MIT, deployed on Vercel, and runs on zero paid infrastructure beyond the data source quotas."

### The pitch that's currently being told, but isn't true yet
> "Bloomberg-grade institutional CRE intelligence platform with deal flow, capital markets analysis, investment portals for Investors / Brokers / Israeli clients, membership tiers (Standard / Accelerated / Institutional), and AI-powered deal intelligence."

Why it isn't true: no auth, no billing, no protected content; deal pages show hardcoded sample numbers; no AI surface anywhere; the membership tiers are marketing copy in a JSON file.

### Positioning recommendation
**Lead with the data terminal.** That's the real product. The institutional/membership/portal framing is aspirational and will burn credibility every time a sophisticated user clicks "Apply" and gets bounced off-domain. Either build the auth/billing/protected-content layer (months of work) or remove the framing and lean into "the most comprehensive free public CRE data terminal."

### Demo story (what to actually show in a 5-minute walkthrough)
1. **Open `/explore`**, type "1600 Pennsylvania Ave NW, Washington, DC 20500" — show the 13-second fan-out, the 16-17 source badges, the live FEMA flood / news / POIs / financing
2. **Open `/data`** — show the Supabase coverage by category and the ingested datasets table with row counts
3. **Open `/wall`** — scroll the live tile grid backed by `data_records`
4. **Open `/sources`** — show the 1,932-source catalog explorer with category filters
5. **Open the WebGL globe** (on `/sources` or auto-injected) — note: turn off the hardcoded fallback first or it'll lie if the dashboard is being audited
6. Skip Index/Site/Terminal for the demo until they're cleaned up — they undermine credibility.

### What's missing for the institutional pitch to be defensible
- Login + role-based access (investor / broker / admin)
- Stripe or Paddle integration
- Protected content behind login (e.g., underwriting tools, full datasets, off-market deals)
- Real (not hardcoded) financing landscape and featured deals
- AI surface — Discovery + Analyst chat + RAG (see Section 11)
- Audit trail / data-provenance UI (which datasets fed which number)

# 20. Final Recommendation

Musharraf — the platform has a stronger foundation than the audit makes it sound. `api/search.py` is the kind of disciplined engineering work that's hard to fake — non-blocking shutdown, stdlib only, real degradation honesty, 22 live providers fanning out in 13 seconds with a deliberate budget cap. The Supabase warehouse is real and ingesting daily. The ADR-001 work was thoughtful. The Phase 0-7 audit captured in `AUDIT.md` was unusually self-critical. **You have a real CRE data terminal underneath.**

The problem is everything stacked on top of it.

**The single most important thing you can do in the next 2 hours is rotate the GitHub PAT and the 14 keys in `api/.env`.** That is not optional. The PAT is push-access. The Supabase service key bypasses RLS. The 11 keys in git history have been publicly downloadable for 5 days. Until you rotate, this audit and every commit since the leak is moot — your security posture is "anyone who looked".

**The second most important thing is to stop the lying-by-UI.** Three pieces of the site present hardcoded numbers as if they were live:
- `index.html:167-176` financing table labeled "FRED + BLS" — the most cynical surface in the codebase
- `dashboard.html:273-282` "Live Search Layers" 20 cards — same file does real probes 20 lines up
- `site.html:401-413` Featured Deal unlabeled — same numbers are correctly labeled `Sample` on terminal
- Plus `globe.js:122-127` hardcoded fallback `1932/16063/14/32`

Fixing these is hours of work, not days. The fix is more valuable than building anything new — because every sophisticated user who scrolls past these surfaces and notices the lie discounts the rest of the platform proportionally. The disciplined work in `/api/search` should not be carrying this weight.

**The third thing is to wire CI.** You wrote tests. They pass. They never run. Add a `ci.yml` with `pytest -m unit` on PR. Add the `if: failure()` notifier to `ingest.yml`. Stop accepting `|| true` as a substitute for handling errors. The aggregate signal across this audit is that the project ships code at a pace that's faster than its self-monitoring — drift between docs and reality, between schema and runtime, between intent and UI labels, between leak-day and rotation-day. The fix for all of those is the same: instrument the boundaries.

**The fourth thing is to decide what RePrime actually is.** Right now there are two products described inside one repo:
- *Product A:* a free, public, institutional-grade CRE data terminal — backed by `/api/search`, `/data`, `/wall`, the warehouse, the catalog. This is what's defensible today.
- *Product B:* a gated investment platform with membership tiers, portals, deal flow, AI intelligence. This is what the marketing copy implies.

You don't have to abandon Product B — but pretending Product B is shipped today undermines Product A. Pick one: either build the auth + billing + protected content + AI surface that Product B requires (months of work — Section 11 has the plan), or strip the framing back to Product A and lean into "the most comprehensive free public CRE data terminal." Don't keep selling the gated product when the gate is an off-domain link.
